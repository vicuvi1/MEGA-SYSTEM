### Database


- Tables: see `src/core/schema.ts` (**append-only**: never edit a shipped migration, add a new one and bump `SCHEMA_VERSION` in `api/_schema.mjs`; a test checks they match). Pages built for an older schema may read but `/api/db` refuses their writes ("A new version is out — please reload"). A migration that MOVES data must run once on the server, never in each browser.
- Server-only tables (`/api/db` refuses them): `sys_auth` (PIN hash, sign-out counter), `sys_login_guard`, `sys_passkeys`, `sys_passkey_chal`, `sys_devices`, `sys_gate` (once-only job slots), `sys_push`, `sys_kv`, `sys_mcp_tokens`, `sys_mem_vec` (Ben's memory embeddings; can always be rebuilt). `cloud_snapshots` is **read-only** from pages.

- **Water and reps: one log (`body_log`, migration 022).** Every glass and set, from any device or bot, is a row with its own id (`id, at, day, kind ('water' | 'reps:<exercise id>'), amount, source, undoes`). Rows are never changed or deleted: a take-back is a negative row, removing a wrong entry is a cancel row (`undoes`), and cancelling that brings it back. Today's numbers are the day's sum (`src/core/bodyLog.ts` pure, `src/main/bodyLog.ts` on the database). Every writer goes through `saveSport` / `logWater` / `logReps` / `logChanges` (app, island, Telegram buttons and undo, Ben, Sporty and automations via `/api/cron?job=sport`); this device's Sport Track copy logs what `updateSport` adds or takes back (`setSportLogger`), the embedded Sport Track app posts `SPORT_LOG` changes to the host, and the Sport Track sync's `finalize` rewrites every copy's today numbers from the log (never "the higher of two copies"). The water history list (`WaterHistory.tsx`, Today's water ⋯ and Body) shows time, amount and source, with Remove / Undo. On each start `repairFromLog` puts a drifted copy right (console + `ls.life_body_repair`). The day the log starts, a copy's earlier number becomes one "logged earlier" row (`seed:<day>:<kind>`, same id everywhere). Simulation: `src/renderer/src/web/waterSync.sim.test.ts`.
- Other `sys_*` tables (never copied to devices): `sys_health` (beats and notes), `sys_error_log`, `sys_ben_log`, `sys_table_versions`, `sys_writes`, `sys_cas`.
- `settings` keys (key → JSON), the main ones: `coach_memory`, `coach_blocks`, `coach_memory_changes`, `coach_profile`, `coach_log`, `coach_mind`, `coach_reminders`, `coach_nudges`, `coach_rhythm`, `coach_rhythm_prefs`, `coach_history`, `coach_letters`, `ben_desk`, `goal_booking`, `sport_tracker_json` (Sport Track's shared copy; its today's water and reps are only a view of the `body_log` table, see below; its day turns at 04:00), `ben_workouts`, `app_sync_finance`, `week_plan`, `focus_running`, `block_marks`, `cal_templates`, `today_order`, `notif_settings`, `ai_models` (your model picks), `ai_budget`, `plugins_on`, `plugin_*`, `pin_hash` (offline copy, written by the server only), `data_version`. The full list, with types and defaults, is `src/core/settingsKeys.ts` (a test fails when code uses a key that is not in it).

### Todoist edits from the app
- Todoist is not in the mirror: the app reads it through `/api/todoist`. Edits go through the edit queue in `web/todoistClient.ts` (pure logic `core/todoSync.ts`): only changed fields, dates resolved to this device's calendar date, your edit shown over any read until Todoist confirms, failed saves kept per device in `localStorage` (`todoist_pending_edits`) and retried. Details in [today.md](today.md) ("Tasks sync with Todoist").
