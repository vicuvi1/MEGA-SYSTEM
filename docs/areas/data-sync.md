### Database


- Tables: see `src/core/schema.ts` (**append-only**: never edit a shipped migration, add a new one and bump `SCHEMA_VERSION` in `api/_schema.mjs`; a test checks they match). Pages built for an older schema may read but `/api/db` refuses their writes ("A new version is out — please reload"). A migration that MOVES data must run once on the server, never in each browser.
- Server-only tables (`/api/db` refuses them): `sys_auth` (PIN hash, sign-out counter), `sys_login_guard`, `sys_passkeys`, `sys_passkey_chal`, `sys_devices`, `sys_gate` (once-only job slots), `sys_push`, `sys_kv`, `sys_mcp_tokens`, `sys_mem_vec` (Ben's memory embeddings; can always be rebuilt). `cloud_snapshots` is **read-only** from pages.

- **Water and reps: one log (`body_log`, migration 022).** Every glass and set, from any device or bot, is a row with its own id (`id, at, day, kind ('water' | 'reps:<exercise id>'), amount, source, undoes`). Rows are never changed or deleted: a take-back is a negative row, removing a wrong entry is a cancel row (`undoes`), and cancelling that brings it back. Today's numbers are the day's sum (`src/core/bodyLog.ts` pure, `src/main/bodyLog.ts` on the database). Every writer goes through `saveSport` / `logWater` / `logReps` / `logChanges` (app, island, Telegram buttons and undo, Ben, Sporty and automations via `/api/cron?job=sport`); this device's Sport Track copy logs what `updateSport` adds or takes back (`setSportLogger`), the embedded Sport Track app posts `SPORT_LOG` changes to the host, and the Sport Track sync's `finalize` rewrites every copy's today numbers from the log (never "the higher of two copies"). The water history list (`WaterHistory.tsx`, Today's water ⋯ and Body) shows time, amount and source, with Remove / Undo. Writes of only today's numbers (`writeView` when the copy's shape is unchanged) bump `savedAt` but keep `editedAt`, and the app sync decides which copy is newer by `editedAt ?? savedAt` (`appSync.ts`); before this a logged set rewrote the shared copy a moment before the sync ran, the server copy looked newer, and an exercise just added on this device (the first set of a new move in Body → Training) was dropped with its set (2026-11-10, `waterSync.sim.test.ts` "a logged set never makes the sync drop a new exercise"). On each start `repairFromLog` puts a drifted copy right (console + `ls.life_body_repair`). The day the log starts, a copy's earlier number becomes one "logged earlier" row (`seed:<day>:<kind>`, same id everywhere). Simulation: `src/renderer/src/web/waterSync.sim.test.ts`.
- **Body composition (`body_comp`, migration 023).** One row per weigh-in from a smart scale or typed; the id comes from the dedupe key (time to the minute + weight to 0.1 kg), and the insert is `ON CONFLICT(dedupe) DO UPDATE … WHERE excluded.updated_at > body_comp.updated_at`, so two devices or sources merge to one row and the later save wins. Every write keeps that day's `body_metrics` weight (first morning weigh-in) and waist filled. Details: [sport.md](sport.md), "Body composition".
- Other `sys_*` tables (never copied to devices): `sys_health` (beats and notes), `sys_error_log`, `sys_ben_log`, `sys_table_versions`, `sys_writes`, `sys_cas`.
- `settings` keys (key → JSON), the main ones: `coach_memory`, `coach_blocks`, `coach_memory_changes`, `coach_profile`, `coach_log`, `coach_mind`, `coach_reminders`, `coach_nudges`, `coach_rhythm`, `coach_rhythm_prefs`, `coach_history`, `coach_letters`, `ben_desk`, `goal_booking`, `sport_tracker_json` (Sport Track's shared copy; its today's water and reps are only a view of the `body_log` table, see below; its day turns at 04:00), `ben_workouts`, `app_sync_finance`, `week_plan`, `focus_running`, `block_marks`, `cal_templates`, `today_order`, `notif_settings`, `ai_models` (your model picks), `ai_budget`, `plugins_on`, `plugin_*`, `data_version`. Food counter: `food_log` (meal details, capped) and `food_goals`; the meal totals are `protein:food` / `kcal:food` rows in `body_log` (see [sport.md](sport.md), "Food counter"). Photo Locker: `vault_index` (metadata only, at most 400 KB; see [vault.md](vault.md)). The full list, with types and defaults, is `src/core/settingsKeys.ts` (a test fails when code uses a key that is not in it).

### Merging two devices' copies (rules, 2026-11-12)
Simulation of each rule: `src/renderer/src/web/syncDataLoss.test.ts`.
- **Desktop offline merge (`merge3` / `mergeRow` in `web/desktopSync.ts`).** A row both sides changed merges column by column (JSON text field by field). Only the real counters in `COUNTER_KEYS` add both changes: `allocated_coins`, `allocated_real_cost` (a goal jar), `count` (items held), and Sport Track's `doneToday`, `currentMl`, `waterMl`. Time columns (`…_at`, `…At`, `ts`, `date`…) as numbers take the later one. Every other clash (weights, positions, start times, titles…) goes to the side whose row or record was changed later by `updated_at` / `updatedAt` / `editedAt` / `savedAt`; with no such time, this desktop's value. Before this, every numeric column was added up (`weight 70 → 72 here, 71 there` became 73).
- **App copies (`web/appSync.ts`).** Which copy is newer is decided only on the shared edit timeline: an edit is stamped `max(this clock, editedAt of the copy it was made on + 1)` (`life_sync_<setting>_seen` keeps that editedAt), and a written copy's `editedAt` is never earlier than the one it merged with. So an edit made after seeing another device's copy always counts as later, even with this clock behind. The edit marker (`life_sync_<setting>_edited`) is cleared once the edit is synced; with no marker, a local change counts as made now. Two edits made truly at the same time on two devices still compare by their clocks.
- **Sport Track (`mergeSport`).** Exercises: every exercise from both copies (the newer copy's order, then ones only the older has); an exercise deleted on either device stays deleted (`exercises` is in `SPORT.lists`, the three-way check against the last synced copy). Sets are kept per set id either way. The day log: a past day changed on both keeps every exercise's count from both (the newer copy's number where both have one); today keeps the higher.
- **Waky (`mergeWaky`).** Mornings, nights and opened chests merge field by field (`mergeEntries`): a field only one side has is kept; a field both have goes to the record with the later `updatedAt` / `editedAt` / `at` / `ts`, else the newer copy.
- **Offline queue (web, `mirror.ts`).** If `life_offline_writes` can't be read, its raw text is first copied to `life_offline_writes_unreadable_<ms>` (repair by hand); if even that copy can't be stored, the queue key is never written again in that tab (new changes wait in memory and the sync status says so).

### Todoist edits from the app
- Todoist is not in the mirror: the app reads it through `/api/todoist`. Edits go through the edit queue in `web/todoistClient.ts` (pure logic `core/todoSync.ts`): only changed fields, dates resolved to this device's calendar date, your edit shown over any read until Todoist confirms, failed saves kept per device in `localStorage` (`todoist_pending_edits`) and retried. Details in [today.md](today.md) ("Tasks sync with Todoist").
- Changes made in Todoist itself: the change check (`/api/todoist {op:'changes'}`, Todoist's incremental sync with a sync token) answers with the changed tasks themselves, done and deleted marked; `todoistClient.changes` puts them right at once (the queue, the known copy, where each task is now). `{op:'lookup', ids, since}` says where tasks the plan still holds went: open on another day, done (a recurring task done today counts, it moved on to its next date), or gone. A task Todoist did not answer for is never guessed at. Rule for a waiting edit vs Todoist: Todoist's newer value wins (see [today.md](today.md)). Due times with a fixed time zone are read in the task's zone (`dueParts` in `src/server/todoistApi.ts`), never as UTC.
