### Database


- Tables: see `src/core/schema.ts` (**append-only**: never edit a shipped migration, add a new one and bump `SCHEMA_VERSION` in `api/_schema.mjs`; a test checks they match). Pages built for an older schema may read but `/api/db` refuses their writes ("A new version is out — please reload"). A migration that MOVES data must run once on the server, never in each browser.
- Server-made backup tables, read-only from pages: `cloud_snapshots` (one row a day: an old one-piece backup or a parts manifest) and `cloud_snapshot_parts` (2026-11-12). Neither is copied to devices (mirror `SKIP`) nor backed up. `restore_stage_*` are a restore's staging tables, dropped by the restore itself (also skipped). No schema migration: the server creates them with `CREATE TABLE IF NOT EXISTS`, like `cloud_snapshots`.
- Server-only tables (`/api/db` refuses them): `sys_auth` (PIN hash, sign-out counter), `sys_login_guard`, `sys_passkeys`, `sys_passkey_chal`, `sys_devices`, `sys_gate` (once-only job slots), `sys_push`, `sys_kv`, `sys_mcp_tokens`, `sys_mem_vec` (Ben's memory embeddings; can always be rebuilt). `cloud_snapshots` is **read-only** from pages.

- **Water and reps: one log (`body_log`, migration 022).** Every glass and set, from any device or bot, is a row with its own id (`id, at, day, kind ('water' | 'reps:<exercise id>'), amount, source, undoes`). Rows are never changed or deleted: a take-back is a negative row, removing a wrong entry is a cancel row (`undoes`), and cancelling that brings it back. Today's numbers are the day's sum (`src/core/bodyLog.ts` pure, `src/main/bodyLog.ts` on the database). Every writer goes through `saveSport` / `logWater` / `logReps` / `logChanges` (app, island, Telegram buttons and undo, Ben, Sporty and automations via `/api/cron?job=sport`); this device's Sport Track copy logs what `updateSport` adds or takes back (`setSportLogger`), the embedded Sport Track app posts `SPORT_LOG` changes to the host, and the Sport Track sync's `finalize` rewrites every copy's today numbers from the log (never "the higher of two copies"). The water history list (`WaterHistory.tsx`, Today's water ⋯ and Body) shows time, amount and source, with Remove / Undo. Writes of only today's numbers (`writeView` when the copy's shape is unchanged) bump `savedAt` but keep `editedAt`, and the app sync decides which copy is newer by `editedAt ?? savedAt` (`appSync.ts`); before this a logged set rewrote the shared copy a moment before the sync ran, the server copy looked newer, and an exercise just added on this device (the first set of a new move in Body → Training) was dropped with its set (2026-11-10, `waterSync.sim.test.ts` "a logged set never makes the sync drop a new exercise"). On each start `repairFromLog` puts a drifted copy right (console + `ls.life_body_repair`). The day the log starts, a copy's earlier number becomes one "logged earlier" row (`seed:<day>:<kind>`, same id everywhere). Simulation: `src/renderer/src/web/waterSync.sim.test.ts`.
- **Body composition (`body_comp`, migration 023).** One row per weigh-in from a smart scale or typed; the id comes from the dedupe key (time to the minute + weight to 0.1 kg), and the insert is `ON CONFLICT(dedupe) DO UPDATE … WHERE excluded.updated_at > body_comp.updated_at`, so two devices or sources merge to one row and the later save wins. Every write keeps that day's `body_metrics` weight (first morning weigh-in) and waist filled. Details: [sport.md](sport.md), "Body composition".
- Other `sys_*` tables (never copied to devices): `sys_health` (beats and notes), `sys_error_log`, `sys_ben_log`, `sys_table_versions`, `sys_writes`, `sys_cas`.
- `settings` keys (key → JSON), the main ones: `coach_memory`, `coach_blocks`, `coach_memory_changes`, `coach_profile`, `coach_log`, `coach_mind`, `coach_reminders`, `coach_nudges`, `coach_rhythm`, `coach_rhythm_prefs`, `coach_history`, `coach_letters`, `ben_desk`, `goal_booking`, `sport_tracker_json` (Sport Track's shared copy; its today's water and reps are only a view of the `body_log` table, see below; its day turns at 04:00), `ben_workouts`, `app_sync_finance`, `week_plan`, `focus_running`, `block_marks`, `cal_templates`, `today_order`, `notif_settings`, `ai_models` (your model picks), `ai_budget`, `plugins_on`, `plugin_*`, `data_version`. Food counter: `food_log` (meal details, capped) and `food_goals`; the meal totals are `protein:food` / `kcal:food` rows in `body_log` (see [sport.md](sport.md), "Food counter"). Photo Locker: `vault_index` (metadata only, at most 400 KB; see [vault.md](vault.md)). The full list, with types and defaults, is `src/core/settingsKeys.ts` (a test fails when code uses a key that is not in it).

### Merging two devices' copies (rules, 2026-11-12)
Simulation of each rule: `src/renderer/src/web/syncDataLoss.test.ts`.
- **Desktop offline merge (`merge3` / `mergeRow` in `web/desktopSync.ts`).** A row both sides changed merges column by column (JSON text field by field). Only the real counters in `COUNTER_KEYS` add both changes: `allocated_coins`, `allocated_real_cost` (a goal jar), `count` (items held), and Sport Track's `doneToday`, `currentMl`, `waterMl`. Time columns (`…_at`, `…At`, `ts`, `date`…) as numbers take the later one. Every other clash (weights, positions, start times, titles…) goes to the side whose row or record was changed later by `updated_at` / `updatedAt` / `editedAt` / `savedAt`; with no such time, this desktop's value. Before this, every numeric column was added up (`weight 70 → 72 here, 71 there` became 73).
- **App copies (`web/appSync.ts`).** Which copy is newer is decided only on the shared edit timeline: an edit is stamped `max(this clock, editedAt of the copy it was made on + 1)` (`life_sync_<setting>_seen` keeps that editedAt), and a written copy's `editedAt` is never earlier than the one it merged with. So an edit made after seeing another device's copy always counts as later, even with this clock behind. The edit marker (`life_sync_<setting>_edited`) is cleared once the edit is synced; with no marker, a local change counts as made now. Two edits made truly at the same time on two devices still compare by their clocks.
- **Synced means the server has it (2026-11-13, `web/appSync.ts`).** After a run writes an app's copy, it asks the SERVER for that setting (`Mirror.serverSetting`: changes still waiting on this device are sent first; a size + start check avoids downloading an unchanged copy) and compares what the server holds with this device's data (`gap`). Only then is the app's status "ok"; otherwise `life_sync_<setting>_unconfirmed` stays set and the next run compares again and sends again (retries 30 s … 10 min). Before this, the desktop counted a copy as synced when it was saved on the PC, and if that upload was then lost ("use server copy", a conflict merge, another writer) it was never sent again.
- **Send back what the cloud lacks.** When only the other side changed (or on a check), the merge is kept here AND, if the merged data has anything the cloud copy lacks, written back: records it doesn't have or has an older edit of, deletions (tombstones), newer settings. "Lacks" is `gapOf` (order-insensitive: list items by content, maps key by key; deletions never count) or the app's own `gap` (Money: `financeGap`, the cloud copy merged with this device's by Finance Helper's own merge with the cloud winning a tie, then compared record by record; the exchange rates only by their day). Union only: nothing is dropped, deletions only through tombstones / the three-way list check. A send of only what the cloud lacked (no edit here) happens at most once a minute per app, so two devices can never trade a copy back and forth quickly.
- **Checks.** Every app compares with the server's copy on start, every 10 minutes, when the internet comes back, on focus / coming back to the window (at most every 2 minutes) and when the desktop's sync dot is clicked (`checkApps` in `tursoWebBridge.ts`), on the desktop and the website alike. A device whose records never reached the cloud sends them on its next start, with nothing to do.
- **Status per app.** Each app (Money, Sport Track, Waky, MAN) keeps its status (`life_sync_<setting>_status`, event `life-app-sync`): ok with the last time the server confirmed it, waiting, skipped with why (Money: "Money PIN needed", see below), or the error text (offline, storage full: the app's data and the agreed copy are written with `setStrict`, never silently). Data center → Sync (was Settings → Data safety) lists them and has **Sync Money now** (Telegram inbox first, then a full compare: "Sent 37 records · cloud up to date"). The desktop's top-bar dot says "Synced" only when Life's tables and every app are confirmed: amber for an error, a skip, a copy waiting, or nothing confirmed for 15 minutes while online; red for an error that old (`appSyncAlert`). Tests: `web/moneySyncHeal.test.ts`.
- **Sync history (2026-11-13, `web/appSync.ts`).** Every run that sent or took something, a skip, a failure, and every "Sync now" (even "nothing to send") is one event in this device's `life_sync_history` (localStorage only, at most 20 per app; the same skip or error in a row is kept once with a count; a full storage keeps fewer, never breaks the sync). Data center → Sync → **Show history** (closed by default) lists them newest first: "13 Nov 21:40 · Money · sent 37 records · cloud up to date", "got 2 records", "skipped (Money PIN needed)", "failed: <first sentence>". Test: `web/moneyLockedSync.test.ts`.
- **Money locked with its PIN (2026-11-13, `web/financeSync.ts` `lockedRound`).** When Money is encrypted on a device (`finance-helper.enc` + `.head`) or the cloud already holds a sealed copy, only a sealed copy travels: `settings.app_sync_finance_sealed = {savedAt, editedAt, box}`, the box being Finance Helper's own `cipher.js` (AES-256-GCM, key from the Money PIN by PBKDF2 with the box's salt). The server never sees the PIN or the plain data. Without the PIN a locked device sends its sealed data as it is, but only while the cloud's sealed copy is the one it last had (compare-and-set inside the write); otherwise it waits with "skipped (Money PIN needed)". With the PIN (Settings → Data safety asks once; kept only in that window's memory, never saved or sent) it opens this device's data, the sealed copy and the plain copy, merges them with Finance Helper's merge (records only added, newer edit wins, deletions by tombstones), keeps this device's copy the way it was kept (re-sealed with this device's salt, or plain on an unlocked device; the app frame merges a waiting save into it), and seals back what the cloud lacks. A wrong PIN or a cloud copy locked with a different PIN than this device's data changes nothing on either side and says so. While the cloud copy is sealed the plain `app_sync_finance` is still read (bots and phone payments add there) but never rewritten from locked data, so server-side Money readers (morning spending, Ask, the bank plugin) see only the copy from before the lock plus bot records. A locked device also drops the usual sync's plain agreed copy (`life_sync_app_sync_finance`) from its storage. Not yet: a way to stop sealing the cloud copy once no device is locked. Test: `web/moneyLockedSync.test.ts`.
- **Money records say where they were changed (2026-11-17).** Finance Helper stamps a record (or account, category, goal…) changed on this device with `editedOn: 'desktop' | 'web' | 'phone'` in the same save; it travels with the record and only names the device in another device's change history (`apps/finance/js/changelog.js`). The change history itself stays on each device (DECISIONS.md). When the stored Money copy changes under an open Finance Helper (another window, Life's sync), the change is logged and the undo base moves to it, so Undo only reverts this window's own steps.
- **Bot saves** (`financeBot.save`, Telegram and quick add) keep the copy's `restore` id and stamp `editedAt` after the copy they changed.
- **Sport Track (`mergeSport`).** Exercises: every exercise from both copies (the newer copy's order, then ones only the older has); an exercise deleted on either device stays deleted (`exercises` is in `SPORT.lists`, the three-way check against the last synced copy). Sets are kept per set id either way. The day log: a past day changed on both keeps every exercise's count from both (the newer copy's number where both have one); today keeps the higher.
- **Waky (`mergeWaky`).** Mornings, nights and opened chests merge field by field (`mergeEntries`): a field only one side has is kept; a field both have goes to the record with the later `updatedAt` / `editedAt` / `at` / `ts`, else the newer copy.
- **Offline queue (web, `mirror.ts`).** If `life_offline_writes` can't be read, its raw text is first copied to `life_offline_writes_unreadable_<ms>` (repair by hand); if even that copy can't be stored, the queue key is never written again in that tab (new changes wait in memory and the sync status says so).

### Todoist edits from the app
- Todoist is not in the mirror: the app reads it through `/api/todoist`. Edits go through the edit queue in `web/todoistClient.ts` (pure logic `core/todoSync.ts`): only changed fields, dates resolved to this device's calendar date, your edit shown over any read until Todoist confirms, failed saves kept per device in `localStorage` (`todoist_pending_edits`) and retried. Details in [today.md](today.md) ("Tasks sync with Todoist").
- Changes made in Todoist itself: the change check (`/api/todoist {op:'changes'}`, Todoist's incremental sync with a sync token) answers with the changed tasks themselves, done and deleted marked; `todoistClient.changes` puts them right at once (the queue, the known copy, where each task is now). `{op:'lookup', ids, since}` says where tasks the plan still holds went: open on another day, done (a recurring task done today counts, it moved on to its next date), or gone. A task Todoist did not answer for is never guessed at. Rule for a waiting edit vs Todoist: Todoist's newer value wins (see [today.md](today.md)). Due times with a fixed time zone are read in the task's zone (`dueParts` in `src/server/todoistApi.ts`), never as UTC.

### Putting a backup back (restore, 2026-11-12)
Runbook: [`docs/RECOVERY.md`](../RECOVERY.md). Code: `core/backupPlan.ts restorePlan` (pure), `tursoWebBridge.ts restoreSnapshot`, `web/restoreApps.ts`.
- **Backup before risk:** `restoreSnapshot` first saves a full backup of today (`backupBeforeRisk('restore')`) and refuses to go ahead when that fails; "Undo to before restore" puts it back.
- **Any size, all or nothing:** the rows go into staging tables (`restore_stage_<table>`, `CREATE TABLE … AS SELECT * … WHERE 0`) in as many small requests as needed (a long text in pieces of 700 k characters), then ONE transaction deletes and refills every table from its staging copy and drops the staging tables. A failure anywhere leaves the real tables untouched and drops the staging tables. Before this, everything went in one request (refused above 4.5 MB).
- **Foreign keys:** tables go in foreign-key order (`fkOrder`, from `PRAGMA foreign_key_list` of the device's copy): children are deleted first, parents filled first; rows keep their order (self-references like `ledger.undo_of`). Before this, tables were deleted alphabetically.
- Rows missing a column keep that column's default (rows are grouped by the columns they carry). Append-only history (`ledger`, `discipline_events`) only gets missing rows back; settings are upserted except `pin_hash`, `bot_bridge_config`, `data_version`; `data_version` moves so every device reloads.
- **The apps' own data:** a backup holds each app's localStorage copy (`APP_BLOBS`: Finance and its locked copy, Sport Track, Waky, MAN). A restore rewrites each app's synced setting as `{savedAt, editedAt, restore: <id>, data}` (`markRestoredApps`) inside the same transaction, and puts the data back on this device (`putBackApps`: this device's own settings stay, Finance through `FINANCE.adopt`). The app sync (`appSync.ts`): a device whose `life_sync_<setting>_restore` differs from the copy's `restore` id takes the copy as it is (no merge, so nothing the restore removed comes back), keeps its own copy from before in `life_sync_<setting>_before_restore`, and remembers the id. Later writes keep the `restore` id on the copy, so a device that was away for weeks still takes the restored copy first. Test: `web/backupBeforeRisk.test.ts`.
- **Restore drill:** `restoreDrill.ts` restores a backup into an empty database built from the migrations and an empty app storage, then compares every table's row count and checksum and every app copy's checksum (`core/backupCheck.ts`). The server runs it weekly on the newest cloud backup; the desktop daily on its newest local backup. Tests: `web/restoreDrill.test.ts` (also with foreign keys enforced and a failure half-way).

### Sync folder (desktop, 2026-11-18)
A live, complete copy of all data in a folder you choose, so the data stays whole when the server (Vercel, Turso) is down.
Data center → Sync → **Sync folder** (moved from Settings → Data safety). Off until a folder is chosen. Desktop only: the website shows nothing.
Recovery steps: [`docs/RECOVERY.md`](../RECOVERY.md) step 2b. Choices not to undo: `docs/DECISIONS.md` "Sync folder".
- **Folder.** Any folder: the picker suggests the OneDrive, Google Drive, Dropbox or iCloud Drive folder when one is found
  (`cloudFolderCandidates`), and a USB drive works too. The chosen folder must exist; the app only makes
  `Life System Sync/<PC name>-<6 letters>/` inside it and never recreates a folder that went missing (a pulled USB
  drive must not turn into a plain folder on the system disk).
- **A copy** is one file, `life-sync-<UTC time>Z.zip`, holding `backup.json` (every table and every app's own data: Finance and
  its locked copy, Sport Track, Waky, MAN; the same format Restore takes), `life-system.sqlite` (this PC's database file),
  `manifest.json` (app version, schema version, device, time, rows per table, each app's size and checksum, and the
  **SHA-256 and size of each file**) and `README.txt`. `backup.json` is the copy a restore uses; the database file is there to
  open in any SQLite viewer.
- **Written whole.** The zip goes to `.~<name>.tmp` (a name cloud-drive apps skip), is flushed to the disk, read back,
  compared byte for byte and opened to check every file against its SHA-256, and only then renamed to its real name. A copy
  that fails the check never gets a real name; the last good one stays, and the panel turns red.
- **When.** 15 s after the last change, at most 60 s after the first one while changes keep coming, and at once on quit,
  sleep and lock (`createPacer`). A change is: the desktop saved the database file (`desktop:save`), or an embedded app
  changed its own data in the window's storage (the `storage` event and the apps' change events → `touch()`). A copy of
  exactly the same data is not written twice (SHA-256 of the database file + the apps' checksums). Big copies are spaced
  out (over 16 MB: one a minute; over 64 MB: one every 5 minutes). No call to the server anywhere on this path.
- **Versions kept:** the newest copy of each of the 24 newest hours, 14 newest days and 12 newest months that have one
  (`versionsToDelete`; a PC that was off keeps its old ones). Files with other names, and other PCs' folders, are never touched.
- **Folder missing** (USB removed, cloud drive paused): the panel says so (amber; red after a day), the app keeps working,
  and the copy is tried again by itself after 30 s, 1 min, 2 min, then every 5 minutes, and on wake / unlock.
- **Restore.** Versions list (this PC's and other PCs') → Preview (date, device, app version, rows, tables, apps; the files
  are checked first) → Restore this version → the app's own `restoreSnapshot` (a "before restore" backup first, all or nothing,
  a restore id on every app copy). A restore needs the server, because it changes the data for every device. While the
  server is down the copies stay whole and open without the app.
- **Encryption (off by default).** "Encrypt the sync folder copy": AES-256-GCM, key from the passphrase by scrypt, file
  `…zip.enc`. The passphrase is kept only on this PC with Electron `safeStorage` (`sync-folder.key` in the app's data folder),
  never in the folder, the database or the settings file. A new passphrase must open the encrypted copies already in the
  folder. With encryption on and the passphrase unreadable, nothing is written (never a plain copy by mistake).
- **A second PC in the same folder** gets its own sub-folder; each PC lists the other's versions and can restore one.
  "Merge from sync folder" is **not built**: `merge()` refuses and changes nothing (design in `docs/DECISIONS.md`).
- **For pages (the Data center):** import `syncFolder` from `src/renderer/src/safety/syncFolder.ts`:
  `available()`, `status()` → `{ enabled, folder, device, lastWrite, lastVerifiedOk, versions, sizeBytes, lastSizeBytes, error, missing, encrypt, passphraseSaved, others }`,
  `suggestions()`, `choose(path?)`, `turnOff()`, `writeNow()`, `listVersions()` → `[{ id, device, mine, at, sizeBytes, encrypted }]`,
  `preview(versionId)`, `restore(versionId)`, `merge()`, `setEncryption(on, passphrase?)`, `open()`. `statusLine(status)` in
  `core/syncFolder.ts` gives the light and the one line of text; `<SyncFolderPanel />` is the ready-made panel. Underneath is
  `window.desktop.syncFolder` (`SyncFolderIpc` in `src/shared/api.ts`; IPC channels `syncFolder:*` in `src/desktop/syncFolder.ts`,
  only the app window may call them, and `choose(path)` takes a path only when it is one of the suggestions found on this PC).
- **Code:** `src/core/syncFolder.ts` (pure: names, versions kept, manifest counts, pacing, status line),
  `src/desktop/syncFolderStore.ts` (files; no Electron), `src/desktop/syncFolder.ts` (Electron: picker, safeStorage, quit / sleep / lock),
  `src/renderer/src/safety/syncFolderClient.ts`, `SyncFolderPanel.tsx` (the panel and the headless `SyncFolderLive`).
  Tests: `src/core/syncFolder.test.ts`, `src/desktop/syncFolderStore.test.ts` (temp folder, fake clock, a damaged read-back),
  `src/renderer/src/safety/syncFolderClient.test.ts`; smoke step "Data center → Sync (Data safety): the Sync folder is hidden on the website…".

### Data center (2026-11-18)
One page for the data (`datacenter/DataCenter.tsx`, page id `data`, a fixed button at the bottom of the sidebar, Ctrl+K, and a link from Settings → Data safety, which now only links there). Rules and numbers are pure and tested in `core/dataCenter.ts`; the readers are `datacenter/usage.ts` and `web/dataUsage.ts`; the controls are `datacenter/actions.ts`. Tabs: Overview · Space · How long · Backups · Sync · Clean up. Backups shows `safety/DataSafetyPanel.tsx` and the weekly check row, Sync shows `SyncPanel.tsx` (the same panels, moved, not copied).
- **Overview.** One health line ("All safe · last backup 2 h ago · synced 3 min ago"; "Needs a look: …" for a red backup, "Nearly full / Filling up: …" for a meter, "Sync needs a look: …") and 4 numbers: closest to a limit, enough for how long, this device's app storage, backup copies kept. Back up now and Sync now (Life's tables, then every app's check, then Money's full compare) are here.
- **Space: one bar per place the data lives.**

  | Meter (id) | Measured from | Limit | Warn / red |
  |---|---|---|---|
  | each app's synced copy (`sync:<setting>`: Money, Sport Track, Waky, MAN; Money's sealed copy when it is the bigger one) | `LENGTH(CAST(value AS BLOB))` of the setting in this device's copy, plus one byte per quote and backslash (as it travels in a request) | 4.5 MB (one request) | 2.5 MB / 3.5 MB |
  | all synced copies and settings together (`settings`) | the same, summed over the `settings` table | 4.5 MB: `mirror.ts readTables` fetches the whole `settings` table in one answer when a setting changed | 2.5 MB / 3.5 MB |
  | app storage on this device (`local`) | localStorage, key + value characters, by key | about 5,000,000 characters | 60% / 80% |
  | browser storage (`browser`) | `navigator.storage.estimate()` | its quota | 70% / 90% |
  | Money change history (`history`) | IndexedDB `finance-helper-changes` | 2,000 entries / 90 days (Finance prunes itself) | none |
  | Life tables (`life`) | every other table, bytes and rows | none (fetched in pages) | none |
  | database file, backup folder (`dbfile`, `backups`; desktop) | IPC `data:usage` (`desktop.dataUsage()`), `backups:status` | none | none |
  | cloud database (`cloud`) | Life tables + settings + the cloud backups' sizes | 5 GB (assumes Turso's free plan; row reads are not measured, no server change) | 60% / 80% |
- **How long.** `forecast` takes every growth estimate there is and uses the FASTEST (so the date is the earliest), rounds the time down, and says what it rests on: Money's own records by the date they were made (last 90 days and last 12 months, `moneyRecords` / `recordRate`; counted twice for app storage, which holds Money and its last synced copy), and the daily size samples (`sampleRate`, needs 14 days). One sample a day: synced sizes in the synced setting `data_size_samples` (every day for 60 days, then one a month, 3 years; one write a day across all devices), this device's app storage in `life_data_samples` (localStorage). Under a year left is amber, under 90 days red.
- **Clean up (each asks in the page and says what it frees).** Money change history older than 7 / 30 / 60 days (device-only data; Undo until you leave the page; not while Money is locked). The copy from before a restore (`life_sync_<setting>_before_restore`): a full "before" backup with the copy inside (`beforeRestoreCopies`) is saved first and the step stops if that fails; Undo puts it back. App caches (service-worker caches; voice models stay). **Deletion marks are only counted, never dropped** (see DECISIONS.md): `prunableTombstones` says which would be safe (older than 90 days and every device in `data_devices_seen` has had Money confirmed since), and each device writes its entry there once a day. Archive old years is a link to Money (it frees no space). Download an app's data: Money (the locked copy when locked), Sport Track, Waky, MAN, Life tables, as JSON from this device.
- **Warnings.** Today's dot (`SafetyDot`) also shows when a meter is past its warning level (amber) or red, and opens the Data center. The desktop sends at most one notification a day in the existing `backup` slot of the 4-a-day budget (`dataNotice`: a red backup first, else the fullest meter).
- **Bridge.** `life.data.usage()`, `life.data.sizeSamples(add?)`, `life.data.devicesSeen(add?)` (all optional, `tursoWebBridge.ts`). No new server code and no `api/` file.
- **Sync folder.** The Sync tab shows the desktop Sync folder panel (`safety/SyncFolderPanel.tsx`, see "Sync folder" in this file; it moved here from Settings → Data safety with the other panels). Where there is no desktop app, a short "Not set up" note (`sync-folder-slot`) says it is a desktop feature.
- Tests: `core/dataCenter.test.ts` (sizes, thresholds, forecast on a pinned clock, samples, the two clean-up plans, the overview line), `web/dataUsage.test.ts`; smoke step "Data center: …".
